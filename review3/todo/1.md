可以把后续工作一次性排到“可交付版本”。下面这份执行单允许 agent 连续开发，不需要每阶段等待确认。

当前 `SystemStatus` 已经保存 `startedAt` 和 `configHash`，第五阶段应复用它们，不能再建立第二套启动时间和编译文件哈希。

现有运行时前端仍明显绑定二阶水箱：`RuntimeSnapshot` 固定包含 valve、tank1、tank2、pid；`mapApiSnapshot()` 和 `TrendBuffer.readTag()` 也硬编码了这些位号。因此“通用运行时模型”必须先于趋势、报警和 HMI。

前端已经有 `recharts` 和 `@xyflow/react`，后续趋势和通用画面优先复用，不新增同类依赖。

# 第二部分：阶段五——运行会话与编译产物生命周期

建议提交：

```text
feat: add managed realtime run sessions
```

## 5.1 目标

解决以下问题：

* 当前选择的工程和正在运行的工程可能不一致；
* 前端目前负责 `compile → start`，无法形成原子事务；
* 编译文件名称可能重复；
* 启动失败、停止和异常退出后的临时文件缺乏统一清理；
* 运行期间修改工程后没有明确版本提示。

## 5.2 后端模型

新增 Go 模型：

```go
type RuntimeSourceKind string

const (
    RuntimeSourceProject    RuntimeSourceKind = "project"
    RuntimeSourceSingleYAML RuntimeSourceKind = "single-yaml"
)

type RealtimeRunSession struct {
    SessionID          string            `json:"sessionId"`
    SourceKind         RuntimeSourceKind `json:"sourceKind"`
    ProjectID          string            `json:"projectId,omitempty"`
    ProjectName        string            `json:"projectName,omitempty"`
    SourcePath         string            `json:"sourcePath,omitempty"`
    RuntimeRevision    string            `json:"runtimeRevision"`
    CompiledConfigPath string            `json:"compiledConfigPath"`
    ConfigHash         string            `json:"configHash"`
    RuntimeName        string            `json:"runtimeName"`
    CycleTime          float64           `json:"cycleTime"`
    OPCUAPort          int               `json:"opcUaPort"`
    APIHost            string            `json:"apiHost"`
    APIPort            int               `json:"apiPort"`
    StartedAt          string            `json:"startedAt"`
    State              string            `json:"state"`
}
```

状态限定为：

```text
preparing
starting
running
stopping
failed
exited
```

`ConfigHash` 和 `StartedAt` 必须最终取自 `SystemBinding.Status()`，不得单独推算第二套权威值。

## 5.3 工程运行版本

在 `internal/realtime` 新增：

```go
func (m *Manager) RuntimeRevision(ctx context.Context, projectID string) (string, error)
```

哈希必须包含：

```text
工程 ID
source 顺序
每个 source ID
replicas
每个 sources/<id>.yaml 的完整字节哈希
alarms.yaml（阶段七加入后）
```

不要包含：

```text
工程显示名称
dashboard.yaml
用户趋势偏好
```

工程改名不应提示“运行组态已变化”；修改来源、副本或报警规则才应提示。

哈希输入必须确定性编码，不能直接依赖 Go map 遍历顺序或文件修改时间。

## 5.4 会话目录

使用用户缓存目录：

```text
<UserCacheDir>/DataFactory/realtime_runs/<session-id>/
```

目录内容：

```text
compiled.yaml
session.json
```

`session.json` 至少记录：

```json
{
  "sessionId": "...",
  "ownerPid": 1234,
  "childPid": 5678,
  "sourceKind": "project",
  "projectId": "...",
  "runtimeRevision": "...",
  "compiledConfigPath": "...",
  "createdAt": "...",
  "state": "running"
}
```

规则：

* 每次启动生成全新 UUID 目录；
* 不覆盖上一轮产物；
* 编译失败立即删除目录；
* DataFactory 启动失败立即删除目录；
* 正常停止后删除目录；
* DataFactory 异常退出后删除目录；
* Wails 应用关闭时先停止子进程，再删除目录；
* 应用启动时清理无存活 owner/child 进程的遗留目录；
* 清理逻辑不能删除当前活跃会话。

文件写入使用：

```text
写临时文件
fsync/close
原子 rename
```

## 5.5 启动事务

新增专门的运行编排绑定，例如：

```go
type RealtimeRuntimeBinding struct {
    manager        *realtime.Manager
    system         *SystemBinding
    sessionManager *realtime.SessionManager
}
```

公开方法：

```go
StartProject(projectID string, options RealtimeStartOptions) (RealtimeRunSession, error)
StartSingleYAML(configPath string, options RealtimeStartOptions) (RealtimeRunSession, error)
Stop() error
GetSession() (*RealtimeRunSession, error)
GetProjectRevision(projectID string) (string, error)
```

`StartProject` 必须在后端完成完整事务：

```text
检查没有实时进程和批量任务
→ 加载工程
→ 计算 runtimeRevision
→ 创建唯一会话目录
→ 编译到 compiled.yaml
→ 调用现有 SystemBinding 启动
→ 等待 API ready
→ 读取 SystemStatus
→ 写入正式 session.json
→ 发布 session 状态
```

任一步骤失败：

```text
停止可能已经启动的进程
→ 删除本次会话目录
→ 清除内存会话
→ 返回原始错误
```

前端不得再执行：

```text
compileProject()
systemApi.start()
```

两个独立调用。

`SystemBinding.Start()` 的现有公共行为保持兼容。可以新增内部 `startManaged()` 或退出回调，但不要破坏旧调用者。

## 5.6 前端会话状态

新增：

```ts
interface RealtimeRunSessionState {
  session: RealtimeRunSession | null
  loading: boolean
  error: string | null
  refresh(): Promise<void>
  startProject(...): Promise<void>
  startSingleYaml(...): Promise<void>
  stop(): Promise<void>
}
```

运行页显示：

```text
正在运行：水箱实时工程
来源：实时工程
运行版本：84f00a12
配置哈希：a06b1c34
启动时间：2026-07-24 23:10:00
周期：0.5 秒
OPC UA：18951
REST/WS：127.0.0.1:8000
```

显示内容必须来自 `RealtimeRunSession`，不能来自当前组态页的 `currentProject`。

用户切换到另一个工程时，运行页仍显示真正运行的工程。

## 5.7 组态变更提示

当存在运行会话且其来源是项目时：

```text
currentProject.runtimeRevision
!=
session.runtimeRevision
```

显示：

> 当前工程组态已修改。正在运行的仍是启动时版本，停止并重新启动后生效。

允许继续编辑，不做热更新，也不自动重启。

## 5.8 停止行为

停止成功后：

```text
停止 DataFactory
→ 等待子进程退出
→ 清理会话目录
→ 清除 RealtimeRunSession
→ 断开 WS
→ 清空强制状态
→ 将当前趋势转为 previous run
→ 清空当前 rawSnapshot/latest frame
→ 位号表显示“已停止”
```

不要把上一轮值继续标记为实时值。

## 5.9 阶段五测试

Go：

* runtime revision 确定性；
* source 顺序或副本变化会改变 revision；
* 工程改名不改变 revision；
* 每次启动生成不同目录；
* 编译失败清理；
  -启动失败清理；
  -正常停止清理；
  -异常退出清理；
  -遗留目录清理；
  -当前活跃目录不会误删；
  -运行工程和当前编辑工程相互独立。

前端：

* 运行卡片显示 session 工程而非 currentProject；
* 组态变化提示；
* 停止后清空当前值；
* 启动失败显示错误；
* 单 YAML 入口仍可用。

# 第四部分：阶段七——项目报警系统

## 7.1 报警配置存储

* 名称非空。

## 7.3 Python AlarmManager

新增：

```text
datacenter/alarm_manager.py
```

每条报警状态机：

```text
normal
pending
active_unacked
active_acked
returned_unacked
```

语义：

高报警：

```text
value >= limit
→ pending
持续 delay_seconds
→ active_unacked
value < limit - deadband
→ returned_unacked 或 normal
```

低报警反向处理。

确认规则：

* active_unacked 确认后变 active_acked；
* active_acked 条件恢复后直接 normal；
* active_unacked 未确认但条件恢复后变 returned_unacked；
* returned_unacked 确认后变 normal。

报警使用真实 runtime snapshot，不使用 UA 强制输出。

计时使用 monotonic clock，事件时间同时记录 wall-clock ISO 时间。

报警计算异常不得阻塞 Engine 周期。

# 第六部分：阶段九——规模、历史和本地安全

建议拆成三个提交：

```text
perf: add runtime tag subscriptions and virtualized tables
feat: add optional realtime run archives
security: protect local runtime API with session tokens
```

## 9.1 大规模位号传输

当前完整 snapshot 每周期广播全部 tag，只适合较小工程。

新增兼容订阅协议：

```json
{
  "type": "subscribe",
  "tags": ["pid.PV", "pid.SV"],
  "includeMeta": true
}
```

要求：

* 旧客户端不发 subscribe 时保持旧全量行为；
* 新客户端只收到订阅 tag 和必要元数据；
* 每客户端独立订阅；
* 慢消费者仍只保留最新帧；
* Engine 只计算一次；
* 修改订阅不重启 Engine；
* 限制单客户端最大订阅数；
* 非法 tag 返回结构化错误；
* 心跳协议保持兼容。

## 9.2 大位号表

Tag catalog 与数值流分离。

位号表：

* 使用虚拟滚动；
* 50,000 行不会创建 50,000 个 DOM 节点；
* 搜索在 tag catalog 上进行；
* 只订阅当前可见结果和用户固定关注项；
* 搜索结果过多时显示结果数量；
* 强制状态仍能正确同步；
* 不允许 UI 阻塞 Engine 或 WS 消费。

## 9.3 可选运行归档

默认关闭。

开启后创建：

```text
<UserDataDir>/DataFactory/run_history/<session-id>/
  metadata.json
  values.sqlite
  alarms.jsonl
```

记录：

* session 信息；
* project/runtime revision；
  -选择的历史 tag；
  -采样时间；
  -真实运行值；
  -报警事件；
  -用户写入事件。

默认不记录所有 50,000 位号，应由用户选择记录 tag，或使用 `display=true` 的 tag。

功能：

* 历史运行列表；
  -打开历史趋势；
  -导出 CSV；
  -删除历史运行；
  -磁盘空间提示；
  -归档失败不影响 Engine 实时运行。

不记录持久化 force 状态；可以记录“发生过强制操作”的审计事件，但重启后不得恢复强制。

## 9.4 本地 API token

每次运行生成随机 session token。

传递方式：

```text
Wails 生成 token
→ 通过环境变量或 CLI 传给 DataFactory
→ REST 使用 Authorization: Bearer
→ WS 使用一次性 query token 或首帧认证
```

要求：

* token 只存在于当前运行内存；
  -不写 project；
  -不输出到日志；
  -运行结束立即失效；
  -旧无 token 模式仅在明确的开发测试开关下允许；
  -默认 API host 仍为 loopback；
  -绑定非 loopback 地址时显示明确安全警告。

# 第十部分：明确禁止项
