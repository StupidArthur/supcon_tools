## P1 · gzip 完全没生效（根因）— **暂缓**

- **严重度**：高
- **现象**：全量 7000+ 条请求中 `content_encoding:"gzip"` 计数 = 0。v0.91->v0.92 加的"HTTP gzip 透明解压"在生产是空转的。
- **证据**：`api_2026-07-26.jsonl` 中所有请求 `content_encoding:""`；统计 `content_encoding:"gzip"` 出现次数 = 0
- **根因**：Ray dashboard（`Python/3.10 aiohttp/3.9.5`）收到客户端发的 `Accept-Encoding: gzip`，但从不返回 gzip 压缩响应。客户端侧的解压逻辑无错，是无对象可解。
- **影响**：预期的带宽优化（200MB/3s -> 20-40MB/3s）从未兑现。响应体保持 5-10 倍体积，是 P2/P3 超时问题的放大器。`GzipSupported` 字段在概览页恒为 false，但用户可能误以为"已优化"。
- **关联**：放大 P2、P3、P6

### 探查结论（2026-07-26 实探 `nlb-2weu6cb4a97uoz9cqu39kvmj.nlb.cn-beijing.volces.com:32414`）

| 路径 | 结果 |
|------|------|
| `/api/v0/state/actors`、`/state/workers`、`/state/nodes` | 全 404，State API 不存在 |
| `/api/v0/actors`、`/api/v0/workers` | 200，但只有身份/状态元数据（actor_id/class_name/state/pid/node_id 等），**零性能指标**（无 CPU/内存/GPU/fds/进程名/exitDetail/requiredResources），且分页限 100 条 |
| `/nodes?view=detail\|full\|all` | 500 "Unknown view"，不存在 |
| Ray 自带 dashboard UI | 浏览器观察同样只用 `/nodes?view=summary` + `/nodes/{id}`，但 detail 是**按需单点**拉，咱们是**批量全扫** |

**根因定性**：Ray 架构上性能指标来自每节点 agent（存 raylet），只有 `/nodes/{id}` 能拿；GCS state store 只存 actor 身份/状态。无批量接口能拿性能数据。endpoint 没得换，请求数和单次体积工具都减不下来。

### 决策

- 工具侧可行方案：① detail 解耦到 30~60s ② 分批轮询削峰 ③ 多集群错峰
- **用户反馈：① ② 无条件做，仅 ③ 错峰可行但暂缓**
- infra 侧（nginx 反代 gzip / 监控搬离生产机）用户也无条件做
- **本条暂缓，仅保留"错峰"作为后续可能。P2/P5/P6 为 P1 衍生表现，待错峰落地后重新评估**

## P2 · cluster-2（NLB）采集实际瘫痪

- **严重度**：高
- **现象**：cluster-2 的 detail 采集退化为"全失败 + 全缓存"，UI 显示的其实是几十轮前的旧数据。
- **证据**：
  - `error_2026-07-26.jsonl`：`ray_http_request_failed` 467 次，全部是 cluster-2 的 `/nodes/{nodeId}`
  - 单个响应 `content_length:~5.1MB`，8s 超时只读到 ~4MB（`decoded_bytes:4152240`）就被掐
  - `collection_stage_failed` 103 次（79 summary + 12 cluster + 12 jobs）
  - 主日志 840 行：`detailMs=40003ms`、`freshNodes=0`、`failedNodes=26`、`reusedWorkers=94`、`reusedActors=1927`、`complete=false`
  - 末期单节点 `consecutiveFailures` 已到 12~20
- **根因**：NLB 链路（`nlb-*.volces.com:32414`）本身慢；叠加无 gzip（P1），单个 `/nodes/{nodeId}` 5MB，26 节点 × 8s 超时 / 10 并发 ≈ 21s 起步，10s 间隔根本跑不完一轮
- **影响**：该集群监控等于失效。`CollectionHealthNotice` 应提示"未刷新"，但用户可能没注意到。告警基于陈旧数据，违反"陈旧数据不告警"原则的边界。
- **注意**：todo.md 第二十六节禁止"只把 Timeout 从 8 秒改成 30 秒"作为伪修复

## P3 · default 集群末期也超时

- **严重度**：中
- **现象**：07:29 附近 default（10.30.144.41:32549）summary 连续超时，触发 detail 无节点可采。
- **证据**：主日志 833/837/844 行 `collect failed stage=summary ... context deadline exceeded`；838/845 行 `detail skipped: no nodes in snapshot`
- **根因**：summary 拿不到节点列表 -> detail 无节点可采 -> 死循环。可能是该集群临时不可达，或与 cluster-2 抢占全局并发（GlobalConcurrency=30）有关
- **影响**：单集群故障，但需确认是否被全局并发挤占
- **关联**：可能与 P2 共用全局 limiter，cluster-2 长时间占用令牌拖累 default

## P4 · environment 日志膨胀 22MB - **已修复**

- **严重度**：中
- **现象**：单日 `environment_2026-07-26.jsonl` 达 22MB。
- **证据**：`ray_response_schema` 记录 4721 条，每条 ~8KB（含完整 `json_shape` 数组，最多 300 条路径）
- **根因**：`observation.go:observeSchema` 设计为"指纹变化即记录"。但不同节点的 Actor 字段组合略有差异（`exitDetail` 有无、`usedResources` 键不同等）-> schema 指纹频繁变化 -> 几乎每次 detail 都落一条
- **影响**：按 30 天保留（`pruneObservationLogs` 保留 30 天），单环境日志潜在 660MB+/月。这是开发期探查用的观测数据，生产环境价值低
- **定位**：`collector/observation.go:45 observeSchema`
- **修复**（2026-07-26）：`observeSchema` 加环境变量 gate，默认关闭。生产不再写 `environment_*.jsonl`；调试时设 `RAY_MONITOR_OBSERVE_SCHEMA=1` 重新开启，无需重新编译。HTTP 请求日志（`api_*.jsonl`，诊断慢节点用）保留。测试 `TestRayObservationLogsSchemaWithoutCookieOrDynamicActorID` 用 `t.Setenv` 显式开启后通过。

## P5 · detail tick 严重滞后未暴露给用户

- **严重度**：中
- **现象**：detail 一轮实际耗时远超采样间隔，但 UI 仍按"10 秒刷新"感知。
- **证据**：cluster-2 `detailMs=40003ms` vs `SampleEvery=10s`；cluster-1 正常 `detailMs~700ms`
- **根因**：collector 的 detail 是顺序 ticker（`collector.go:207 case <-detailTick.C`），一轮没跑完下个 tick 被丢弃。实际每 ~40s 才更新一次数据，75% 的 tick 被跳过
- **影响**：用户以为 10 秒刷新，实际 40 秒。`PerfMetrics.Risk` 只看 `DetailMs > periodMs*80%` 判 danger，40s 远超 8s 阈值应已报 danger，但需确认前端是否真的展示了 risk=danger
- **关联**：P2 的直接表现

## P6 · 大响应体无防护

- **严重度**：中
- **现象**：单个 HTTP 响应体积异常大，无 gzip 时形成带宽冲击。
- **证据**：
  - cluster-1 `/nodes?view=summary` 单次 `decoded_bytes:10200939`（~10MB）
  - cluster-2 `/nodes/{nodeId}` 单次 `content_length:~5.1MB`
  - `maxResponseBytes` 上限 64MB（`ray_client.go:20`），放行了这些大响应
- **根因**：Ray dashboard 对大集群返回的 summary/detail JSON 本身就大；无 gzip（P1）放大 5-10 倍
- **影响**：N 个并发大响应打爆网络与内存。cluster-1 靠局域网快链路（133ms）勉强扛住，cluster-2 走 NLB 就崩
- **注意**：降 `maxResponseBytes` 会误伤合法大集群；真正解法是 P1（gzip）或服务端字段裁剪
