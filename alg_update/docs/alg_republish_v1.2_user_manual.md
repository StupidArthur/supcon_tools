# 算法重发布工具 v1.2 用户手册

模拟"运维想让平台所有已发布算法的实例都重新拉起"这件事：对平台每一个 `isRelease=1` 的算法，按顺序做「取消发布 → 等 1 秒 → 重新发布」三步，让 Pod 走一次完整的下线再上线流程。本工具**不读本地文件、不读 CSV、不上传任何代码包**——只动平台状态。

产物：`算法重发布工具v1.2.exe`（单文件 exe，无需装 Python）。

---

## 1. 这是什么

平台上的算法实例（Pod）一旦跑起来，新改的核数/副本数/位置配置不一定能即时生效。最稳的办法是「**取消发布 → 等一下让平台清理 → 重新发布**」。本工具对**所有**已发布算法自动做这件事：

```
取消发布 → time.sleep(1 秒) → 重新发布
```

每个算法处理时**用平台当前的 `cores / resourceType / numReplicas`**，也就是重发布后参数和重发布前一致——本工具只让实例重建，**不修改**核数、副本、发布位置这些参数。要改这些参数用「算法发布工具 v1.2」。

中间那 1 秒停顿是**硬编码**的（写在源码里），不可改。它的作用是给平台侧完成下线清理留时间——少了会让重新发布失败 / 状态错乱。

## 2. 怎么使用

### 2.1 启动

双击 `算法重发布工具v1.2.exe`。窗口标题：`算法重发布工具 v1.2  |  designed by @yuzechao`。

### 2.2 一次完整的重发布流程

1. **填连接信息**（URL / Username / Password；HTTPS 才填 Tenant ID）。
2. **点「查看已发布算法」**（蓝色按钮）—— 工具登录平台 → 拉全量算法 → 过滤 `isRelease=1` → 在「已发布算法列表」区显示出来。**「执行发布流程」按钮此时变为可用**（之前是灰的）。
3. **扫一眼列表** —— 确认数量和算法对得上你预期的（这一步不是真改平台，看错成本很低）。
4. **点「执行发布流程」**（红色按钮）—— 工具按列表顺序逐个算法执行「取消 → 等 1 秒 → 重发」，「操作日志」区实时输出每步的 ✓ / ✗。
5. **看日志确认跑完** —— 末尾输出 `全部处理完成`。

### 2.3 停止 / 中断

工具没有「中止」按钮。点了「执行发布流程」之后只能关窗口，后台线程会跑到当前算法结束才停。每步都打日志，关窗口前先看日志确认跑到哪儿了。

### 2.4 已发布算法为 0

「查看已发布算法」点完后，如果平台确实没有 `isRelease=1` 的算法，列表区显示「无已发布的算法」，日志打 `[提示] 没有已发布的算法，无需处理」，**「执行发布流程」按钮保持灰**——可以直接关窗口。

## 3. 需要填写什么

「连接配置」区 4 个字段：

| 字段 | 默认值 | 必填 | 备注 |
|---|---|---|---|
| **URL** | `http://10.16.11.1:31501` | 是 | 平台 alg-manager-web 的 HTTP/HTTPS 地址 |
| **Username** | `admin` | 是 | 平台账号 |
| **Password** | （空） | 是 | **每次启动都要重新填**，不会记忆 |
| **Tenant ID** | （空，仅 HTTPS 显示） | HTTPS 必填 | URL 是 `http://` 时输入框自动隐藏 |

> 本工具没有「算法目录」「CSV 文件」「并发数」这类输入框——它是纯平台状态操作，不需要任何附件。

---

## 4. 需要准备什么附件

**不需要任何附件**。

没有 CSV、没有本地文件目录、不需要上传包——本工具只对平台已发布算法执行取消 + 重新发布两步。

## 5. 界面上怎么看、怎么判断该做什么

工具窗口从左到右 5 个区：

### 5.1 「连接配置」区

详见第 3 章。

### 5.2 两个操作按钮

| 按钮 | 颜色 | 何时可点 | 干的事 |
|---|---|---|---|
| **查看已发布算法** | 蓝 | 总是可点 | 登录平台、拉已发布算法、显示列表、让「执行」按钮变可点 |
| **执行发布流程** | 红 | 仅当「查看」完成后且列表非空 | 逐个算法跑「取消 → 1 秒 → 重发」 |

执行期间两个按钮都变灰。

### 5.3 「已发布算法列表」区

「查看已发布算法」点完后显示：

```
  PID辨识分析  |  id=101  |  CPU  |  核数=2  |  副本=1
  PID数据处理  |  id=103  |  CPU  |  核数=1  |  副本=1
  valve_anomaly_detection_train  |  id=205  |  GPU  |  核数=2  |  副本=1
  ...
```

每行格式：`算法名 | id | CPU/GPU | 核数=N | 副本=N`。

**怎么判读**：

- 列表非空 → 可以执行；执行后这些算法都会经历「取消 → 1 秒 → 重发」，实例会重建。
- 列表为空 → 直接关窗口，无需执行。
- 如果列表里出现**不该重建**的算法（生产关键算法、当前正在被外部调用的）——**关掉工具，去平台后台手动取消那个算法再点重发**，或者干脆别跑这个工具。**点「执行发布流程」是对列表里全部算法生效**。

### 5.4 「操作日志」区（执行过程的真实记录）

每处理一个算法打一段：

```
[1/5] ========== 开始处理: PID辨识分析 ==========
  id=101  CPU  核数=2  副本=1
  >> 取消发布...
  << 取消发布成功
  >> 等待 1 秒...
  << 等待结束
  >> 重新发布...
  << 重新发布成功
[1/5] ========== 处理结束 ==========

[2/5] ========== 开始处理: PID数据处理 ==========
  ...
============================================================
全部处理完成
============================================================
```

**怎么判读**：

| 日志 | 含义 |
|---|---|
| `>> 取消发布...` / `<< 取消发布成功` | 取消发布这一步成功 |
| `>> 等待 1 秒...` / `<< 等待结束` | 硬编码 1 秒停顿，到点后继续 |
| `>> 重新发布...` / `<< 重新发布成功` | 重新发布成功 |
| `<< 取消发布失败: <错误>` | **这个算法被跳过**，工具 `continue` 到下一个算法，不会再发重发布 |
| `<< 重新发布失败: <错误>` | 取消成功但重新发布失败——算法最终状态是「未发布」，需要人工去平台把它重新发出来 |
| `(可能是登录已过期，请重新登录)` | 鉴权类错误，重启工具重新填密码 |
| **末尾汇总** `全部处理完成` | 全部算法都跑过一轮（不一定都成功） |

每处理完一个算法，无论成功失败，工具都会继续处理下一个，**不会**因为单个算法失败而中断全流程。
